## Description

This Spring Boot API helps students report lost items and lets campus custodians manage claims, found desks, item categories, and return receipts. It uses the entities and endpoint rules from the Web Technology and Internet mid-term examination.

- Java 21
- Spring Boot

- PostgreSQL
- Maven
- Postman

## PostgreSQL setup

Install PostgreSQL and make sure its service is running. Create the database as the `postgres` user from PowerShell:

```powershell
psql -U postgres -f .\database\setup.sql
```

The script creates the `campus_lost_found` database. Hibernate creates or updates the tables when the API starts.

Copy `.env.example` to `.env` to keep a local reminder of your database settings. Spring Boot does not load `.env` files by itself; set the variables in PowerShell, VS Code, or your IDE before starting the API. Do not commit real passwords.

```powershell
$env:DB_URL = "jdbc:postgresql://localhost:5432/campus_lost_found"
$env:DB_USERNAME = "postgres"
$env:DB_PASSWORD = "your_local_postgres_password"
```

The default URL and username are in `application.properties`. `DB_PASSWORD` defaults to an empty value, so set it if your PostgreSQL user requires a password.

## Build and run

Install Java 21, open this folder in VS Code, and run the Maven wrapper in PowerShell:

```powershell
.\mvnw.cmd test
.\mvnw.cmd spring-boot:run
```

The API listens at `http://localhost:8080`. The datasource must be available when running the application. The Maven test command can run the unit tests without a PostgreSQL connection.

## API endpoints

All endpoints use JSON unless they return a plain text message. UUIDs are generated by the API. Save referenced objects first, then use a GET all endpoint to read their IDs. Save endpoints return the message in the examination, not the saved entity.

### A2: CRUD

| Entity | Save | List all | Get one | Update | Delete |
|---|---|---|---|---|---|
| Item category | `POST /api/item-categories/save` | `GET /api/item-categories/all` | `GET /api/item-categories/{id}` | `PUT /api/item-categories/update/{id}` | `DELETE /api/item-categories/delete/{id}` |
| Found desk | `POST /api/found-desks/save` | `GET /api/found-desks/all` | `GET /api/found-desks/{id}` | `PUT /api/found-desks/update/{id}` | `DELETE /api/found-desks/delete/{id}` |
| Custodian | `POST /api/custodians/save` | `GET /api/custodians/all` | `GET /api/custodians/{id}` | `PUT /api/custodians/update/{id}` | `DELETE /api/custodians/delete/{id}` |
| Student | `POST /api/students/save` | `GET /api/students/all` | `GET /api/students/{id}` | `PUT /api/students/update/{id}` | `DELETE /api/students/delete/{id}` |
| Item claim | `POST /api/item-claims/save` | `GET /api/item-claims/all` | `GET /api/item-claims/{id}` | `PUT /api/item-claims/update/{id}` | `DELETE /api/item-claims/delete/{id}` |

Save endpoints return HTTP 201 and a success message. Item claim updates leave the status unchanged; use the status endpoint to change it.

### Business and receipt endpoints

| Requirement | Method and path |
|---|---|
| D2 | `PATCH /api/item-claims/{id}/status?status=MATCHED` |
| D3 | `PUT /api/custodians/{custodianId}/item-categories/{itemCategoryId}` |
| D4 | `PATCH /api/custodians/{custodianId}/found-desk?deskNumber=4` |
| E1 | `POST /api/return-receipts/save?itemClaimId={itemClaimId}` |
| E2 | `GET /api/return-receipts/student/{regNumber}` |
| E3 | `DELETE /api/return-receipts/delete/{id}` |
| F2 | `PATCH /api/item-claims/cancel-day?custodianId={custodianId}&date=2026-10-30` |

An item claim can move from `REPORTED` to `MATCHED` or `WITHDRAWN`, then from `MATCHED` to `RETURNED` or `WITHDRAWN`. `RETURNED` and `WITHDRAWN` are final statuses. A return receipt can only be saved for a `RETURNED` claim.

## Sample data and the date rule

Use the collection's **Step 0 - Sample data** requests to create the four categories, four desks, three custodians, five students, and ten claims. Run this folder once against an empty database; running it again creates duplicate records and can make the safe-save checks reject requests. The requests save the generated IDs as collection variables and use those IDs for later requests. The sample includes two students named Mugisha, an unused Keys category, and an unoccupied desk.

The examination asks for two claims on `2026-10-20`, but the system date for this project is `2026-10-30`. The required safe-save rule rejects every claim date before today. Therefore an October 20 claim cannot be created through the save API while that rule is active. The Postman sample uses October 30 and November dates instead, and includes a past-date request that demonstrates the required HTTP 400 response. This keeps the business rule intact instead of inserting historical sample claims around it.

For each claim, the API ignores a status supplied in the save JSON and starts it as `REPORTED`. Use PATCH requests to move a claim through valid status transitions.

## Postman testing

1. Start PostgreSQL and the Spring Boot application.
2. Import `campus-lost-and-found-system-midterm.postman_collection.json` into Postman.
3. Keep the collection's `baseUrl` value as `http://localhost:8080` or change it to your local URL.
4. Run the **Step 0 - Sample data** folder in order. Its tests store generated IDs in collection variables.
5. Run the requirement folders in order. Requests marked **Expected error** deliberately show the specified 400, 404, or 409 response.

If running individual requests, run the matching save request, call its GET all endpoint, and copy the generated `id` from that response. Use that UUID in the related path or relationship JSON.
